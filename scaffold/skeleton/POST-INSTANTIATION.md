# Post-instantiation — verification checklist

This repository was generated by an AI agent operating the Hipocampo skill, following the declared scaffold profile (`hipocampo/scaffold/profiles/pessoal.yaml` or `empresa.yaml`) — see `hipocampo/skill/references/instantiation.md`. The agent already presented the complete plan before writing any file (invariant 5) and generated the outputs declared in the profile. This checklist exists for you to confirm the generation was done correctly before storing any real knowledge — it is no longer a manual step-by-step instantiation guide.

## 1. Confirm that the repository is private

This is not optional. It's the invariant that underpins the methodology's entire `visibility` model (`hipocampo/SPEC.md`, section 8, invariant 1). The agent should already have created the repository as private — confirm it.

## 2. Confirm the LICENSE

The agent should already have generated the `LICENSE` from the correct template (personal or corporate, `hipocampo/scaffold/license-templates/`), with the placeholders filled in from the inputs you provided. Open the file and check:

1. Name/handle (personal) or legal name (corporate) filled in correctly.
2. If this repository is at the "vault" level (only receives `visibility: confidential`/`restricted`), confirm that only sections (c) and (d) of the template were kept, per the template's own adjustment note.

## 3. Confirm the skill is installed in your AI environment

This content repository **does not** carry a `skill/` folder — the skill always runs in your AI environment (Cowork, Claude Code, etc.), per person, never per repository (`hipocampo/decisions/0025-skill-is-client-side-never-per-repository.md`). The scaffold never generates this folder.

1. Read `skill/manifest.yaml` from the canonical repository default branch only to discover the current package version and `updates.release_ref`. Obtain the skill files, `manifest.yaml` and `package-lock.yaml` from that versioned release tag, not from `main`. Confirm the GitHub Release reports `immutable: true`, its tag resolves to the release target, pin that commit, verify every package-lock hash, then install the exact skill version after operator confirmation. `main` is availability metadata only.
2. If this new repository is your personal anchor Vault and you want to use it for discovery, confirm its address is recorded as an optional pointer per `skill/references/personalization.md`. A personal anchor is not required for authorized reading of another entity Vault. Without one, use a confirmed invitation/address or bounded private project hints and revalidate the remote target each session; this is not a complete inventory.
3. If you choose a personal anchor and operate more than one git account for the same human author, confirm the handles in your private `profile.md` (`hipocampo/SPEC.md` section 12-B). Without a personal anchor, do not create `profile.md` in an entity Vault just to satisfy this checklist.

## 4. Confirm the AGENTS.md

`AGENTS.md` should already have been filled in by the agent from the collected inputs before generation — not a generic `[fill in: ...]`. Check:

- **Scope of this repository** — the declared entity, role, explicitly chosen Vault profile, separate policy profile, curation level, language and what should/shouldn't be stored here.
- **Multi-account author identity**, if applicable.
- **Local extensions to Hipocampo vX.Y** — if there's nothing to declare yet, it should be recorded as "none yet", not left blank.
- **Maintenance rituals** — cadence confirmed (default or this instance's actual adjustment).

## 5. Confirm the compatibility version

In the same `AGENTS.md`, check the "Hipocampo version followed by this instance" line — it should reflect the current version of `hipocampo/SPEC.md` at instantiation time, not an outdated value.

## 6. Confirm the `hipocampo.yaml` manifest

This repository should have a `hipocampo.yaml` at the root, generated by the agent from the scaffold profile used. Check that `instance.vault_profile` is your explicit choice (`team`, `personal` or `entity`) and that `instance.entity`, `instance.role`, `instance.policy_profile`, `instance.curation_level`, and `scaffold.profile` correctly reflect this instance. The suggested `team` profile is never filled from silence. A legacy `instance.tier` is accepted only for a pre-2.1 manifest awaiting upgrade.

## 7. Delete or adapt the example

`example/exemplo-nota.md` exists only to illustrate the frontmatter — it isn't real content. Delete or adapt it before your first real document.

## 8. Confirm repository line endings

Confirm that the generated `.gitattributes` is committed and that authored
text uses LF in the Git blob and working tree. Binary files and any approved
exact-byte historical sources need their own explicit exceptions. Do not
renormalize existing content as part of this check; see the source
methodology's `docs/line-endings.md`.

## Done

From here, follow `hipocampo/GETTING-STARTED.md` (section 3 onward) to write your first document and set up the routines (frontmatter audit, REM, structural audit), already covered by the skill you confirmed in step 3.

## V3 activation gate

For stable, confirm the published immutable methodology release, the skill version and package hashes named by its canonical manifest, and the vault ^3.0.0 tuple. Verify the GitHub Release reports `immutable: true`, its tag resolves to the release target, pin that commit and check every package-lock hash. Verify the actor, authorized vault scope and canonical CRUD capability. Accept the first active Collection before creating any Record. The example is proposal documentation, not a Record; do not turn it into knowledge by direct editing. No inbox is generated. Block activation if any required declaration or capability is unknown.

For explicitly selected experimental execution, resolve the pinned source commit
or RC tag and distribution hashes instead; no GitHub Release or future stable is
required. Candidate/final-readiness state emits WARNING and valid canonical
operations continue. Authorization, compatibility and integrity remain required.
See the selected source's docs/v3-runtime-usage.md; this creates no Record or
permission. Template variables must be filled before instance activation.
