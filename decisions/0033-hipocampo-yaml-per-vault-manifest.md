# 0033 — `hipocampo.yaml` manifest per vault

**Status:** Accepted

## Context

`moda.yaml`, introduced in Phase B of MODA conformance work, declares `hipocampo`'s (the methodology's) relationship with MODA — it says nothing about the relationship between an individual vault (e.g., `hipocampo-personal-vault`) and the version of `hipocampo` it follows. That information today lives only in the "Hipocampo version followed by this instance" line of each vault's `AGENTS.md` — free text, no schema, not machine-queryable.

With the scaffold consolidated into `hipocampo/scaffold/` (`decisions/0032`), each vault is now generated by a declared profile (`pessoal` or `empresa`) from a specific `hipocampo` commit. This provenance — which profile, which engine version, which source commit — also had nowhere to be recorded.

## Decision

Every vault generated by the scaffold receives, at its root, a `hipocampo.yaml` manifest, in the same spirit as the methodology's `moda.yaml` but scoped to the instance:

```yaml
hipocampo:
  manifest_version: "1.0"
  compatibility: "^1.9.0"
  verified_against: "<SPEC.md version at the time of instantiation>"
  verified_commit: "<hipocampo/main commit used as the source>"

instance:
  repository: "<URL of this repository>"
  domain: "pessoal | empresa"
  tier: "conteudo | vault"

scaffold:
  profile: "pessoal | empresa"
  profile_version: "..."
  engine_version: "..."
  source_repository: "https://github.com/mklagenberg/hipocampo"
  source_commit: "<same commit as hipocampo.verified_commit>"

skill:
  generated_by_version: "<version of the personal skill that ran the instantiation>"

state: "current"
```

`instance.domain` uses the most recent vocabulary (`pessoal`/`empresa`, `decisions/0029`) — not the original vocabulary of the `AGENTS.md` "Instance type" field (`pessoal`/`corporativa`). This divergence is known and deliberately **not** resolved by this DR (see rationale).

Consequence: since every existing vault eventually needs to gain this manifest to remain conformant with the methodology (`UPGRADE.md` gains a new item), this is one more piece reinforcing the MAJOR nature of the jump to v2.0.0.

## Rationale

The manifest separates two things that today are mixed together as free text in `AGENTS.md`: the operational declaration a human reads and edits (scope, local extensions, rituals) and the provenance that a tool would ideally query (which commit this vault came from, which profile, compatible with which version). Machine-readability is also what MODA already asks of `hipocampo` itself — replicating the pattern into each vault is consistent.

The vocabulary divergence (`domain: pessoal|empresa` vs. "Instance type: pessoal|corporativa") is intentionally left as is, not harmonized now: changing the `AGENTS.md` field would require editing every existing `AGENTS.md` (`hipocampo-personal-vault`, `hipocampo-concepts`, `hipocampo-company`, `hipocampo-company-vault`), an operation of larger scope than this Phase D set out to cover. Better to name the problem here — explicitly, in writing — than to silently resolve it in only half the places it appears.

## Discarded alternatives

- **Keep this information only in `AGENTS.md`, without a separate manifest.** Discarded: it mixes operational text (edited by a human) with provenance (which should ideally be generated and, ultimately, machine-verified) — the same argument that already led `moda.yaml` to exist separately from the methodology's `README.md`/`AGENTS.md`.
- **Harmonize the vocabulary now, editing every existing `AGENTS.md`.** Discarded this round: larger scope than Phase D set out to cover, and risky to edit four real content repositories as a side effect of a manifest change. Recorded as a known pending item.
- **Call the field `kind` instead of `domain`.** Discarded: `kind` is already used with a different meaning in `moda.yaml` (`artifact.kind`, methodology vs. framework) — reusing the name for a different concept within the Hipocampo/MODA ecosystem itself would generate confusion.
