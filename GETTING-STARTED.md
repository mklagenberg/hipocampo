# Getting started with Hipocampo V3

The V3.0.0 contract and skill 2.0.0 are prepared for final review. Verify actual
immutable publication before installation or durable V3 operation. Existing
V2 instances keep the appropriate immutable V2 package until governed
migration. The [previous guide](GETTING-STARTED-V2.md) is historical; its flat
frontmatter examples are not the V3 schema.

## 1. Confirm the boundary

Name the entity, target private vault, owner, authority, policy, scope and
requested operation. Repository/account access is not operation approval.
Keep personal and corporate governance separate; metadata and knowledge are
different surfaces. Read [SPEC](SPEC.md) and the target vault's instructions.

## 2. Verify versions and capabilities

Verify the actual methodology release/tag/commit, the skill package and its
lock, and the vault declaration. V3 target: 3.0.0 / 2.0.0 / ^3.0.0. Unknown or
incompatible tuples block V3 writes. Verify each actual adapter operation;
portable instructions do not prove that every host exposes canonical CRUD.
The demonstrated adapter is bounded local Python/Git. Global installation
requires the operator's explicit action; no silent update.

## 3. Set up a new vault

Use the selected personal/corporate scaffold from the verified immutable
release. Collect every required input and present the exact private-repository
creation plan. Metadata uses an independently authorized structure capability;
RecordCrud is for Records. Stop on missing capability or conflicting files.
Accept an initial active Collection before the first knowledge Record.
Scaffold examples are proposals, not persisted Records. No V3 inbox exists.

## 4. Admit knowledge

Keep raw/sensory capture outside the vault. Prepare a Record with non-empty
prose, stable identity, source, entity, scope, governance, active Collections,
privacy, epistemic and temporal state. Preserve uncertainty and actual source
limitations. Obtain the required semantic/human decisions, then canonical
CRUD performs deterministic validation and persistence. Never write Records
through direct files or a GitHub contents API.

## 5. Retrieve the minimum needed

Confirm actor and a non-empty authorized vault scope. Read metadata through
its authorized metadata capability; retrieve Records/Chunks through canonical
Read/Search. Filter frontmatter first. Select only relevant content and keep
Chunk parent context. L4 expansion needs explicit authorization. Inaccessible
Artifacts do not erase persisted Record prose; no implicit Artifact fetch.

## 6. Maintain and migrate progressively

Use separate frontmatter, staleness and semantic queues under meta/. Reads
flag findings without writes. Each correction uses the required gate and CRUD.
For existing content, use [MIGRATIONS](MIGRATIONS.md) and
[execution/recovery](docs/v3-migration-execution.md): inventory, full review,
accepted mapping and Collections, fingerprints, preflight, pilot, canonical
apply, fresh reload and conservation checks. Reconcile partial effects before
retrying. Recovery needs an exact ticket and explicit approval.

## 7. Keep proof limits visible

A structural pass proves structure, not truth, authority, human acceptance,
remote enforcement or publication. Report partial coverage, retained items,
failures and next decisions. The release and each vault adoption are distinct.
