# Hipocampo — Getting Started

Practical guide to adopting the methodology. For the complete normative specification, see [SPEC.md](SPEC.md). For what Hipocampo is not and where it doesn't apply, see [DISCLAIMER.md](DISCLAIMER.md). If you've never used git/GitHub, start with the [fundamentals doc](docs/FUNDAMENTALS.md).

## 0. If you're learning the methodology for the first time

Before instantiating anything, here's a reading order that avoids backtracking:

2. **This document, start to finish** — the practical mechanics.
3. **[BEST-PRACTICES.md](BEST-PRACTICES.md)** — day-to-day judgment, privacy, team adoption — after the mechanics already make sense.
4. On demand, when the question comes up: **[SPEC.md](SPEC.md)** (the full norm), **[docs/AI-MODELS.md](docs/AI-MODELS.md)** (what matters in an AI agent to operate this well) and **[docs/PERFORMANCE-AND-GRAPH.md](docs/PERFORMANCE-AND-GRAPH.md)** (how retrieval works, and the relationship with Google's OKF).

If you've already instantiated a repository and just want the immediate step-by-step setup, skip to section 2 below and to the `POST-INSTANTIATION.md` generated by the agent inside your new repository (source template: `scaffold/skeleton/POST-INSTANTIATION.md`).

## 1. Understand the architecture before creating anything

Hipocampo separates two types of repository:

| Layer | What it stores | Visibility |
|---|---|---|
| Methodology and tooling (`hipocampo`, including `scaffold/` and `skill/`) | Spec, rules, scaffold, skill — never real content | Public |
| Knowledge base (any repository instantiated by the agent from the scaffold in `hipocampo/scaffold/`) | The actual content — notes, decisions, projects, people | **Always private, no exceptions** |

You never edit `hipocampo` to store your own knowledge. It's the spec and the scaffold; your knowledge lives in a separate, private repository, instantiated from the scaffold.

## 2. Instantiate a content repository

There's no longer a "Use this template" button — instantiation is carried out by an AI agent operating the Hipocampo skill (see `skill/references/instantiation.md`), from a profile declared in `scaffold/profiles/` (`pessoal.yaml` or `empresa.yaml`, `decisions/0032`). If this is genuinely your first vault ever, the agent runs this as part of the Bootstrap mechanic (`SPEC.md`, section 12-B) — including a conversational walkthrough first if you're new to Hipocampo (`docs/getting-started-non-technical.md`) — rather than as a bare instantiation request; for a second or later vault, it's just this procedure directly.

1. Ask the agent to instantiate a new repository, providing: repository name, which **entity** it belongs to and whether it's the entity's **anchor** vault or an **additional** one (`SPEC.md`, section 2-C), curation level (`content` or `vault` — same section), and the owner's identity.
2. The agent reads the corresponding profile, gathers any missing input, and **presents the complete plan before writing anything** (invariant 5, `SPEC.md` section 8) — repository to create, each file to generate, LICENSE chosen.
3. After you confirm, the agent creates the repository (**private — not optional**, invariant 1) and generates every output declared in the profile: `AGENTS.md` and `hipocampo.yaml` already filled in with the collected inputs, `LICENSE` already from the right template (`scaffold/license-templates/`), `CLAUDE.md`, `POST-INSTANTIATION.md`, `registry.md`, `example/example-note.md`.
4. The new repository **does not** get a `skill/` folder — the skill always runs in your AI environment, per person, never per repository (`decisions/0025`). If you don't have one yet, install your own personalized copy from [`skill/SKILL.md`](skill/SKILL.md) + `skill/references/*.md` (this repository, the canonical source). There's no router table to fill in — if this new repository is your personal anchor vault, record its address per `references/personalization.md`; otherwise nothing local needs updating, discovery picks it up automatically from its own manifest (`SPEC.md`, section 12-A).
5. Once generated, follow the new repository's `POST-INSTANTIATION.md` — now a **verification** checklist, not a manual step-by-step: it confirms the agent generated everything correctly before you store any real knowledge.

Full operational detail (who does what, in what order, what to present before writing): `skill/references/instantiation.md`. For the Bootstrap mechanic wrapping this on a first vault: `SPEC.md`, section 12-B.

## 3. Write your first document

Every document is a `.md` file with the frontmatter from SPEC.md (section 2). A minimal example, for a new note:

```yaml
---
title: "Document name"
date: "2026-07-27"
updated: "2026-07-27"
source: "conversation"
tags: []
type: "note"
temporality: "evergreen"
ttl: "2028-07-27"
status: "active"
related: []
revision: 1
visibility: "internal"
author: "Your Name - @your-github-username"
---
```

Fill in `type` (SPEC section 3) and `temporality` (section 5) thinking about the document's actual purpose — don't force a value just because it seems the most common. If no existing `type` fits, re-read the expansion rule before creating a new value.

## 4. Cross-repository references

If you maintain more than one content repository (for example, a personal one and a work one), use `related: ["$alias:path.md"]` to point from one to the other, and keep a `registry.md` in the least restricted repository of each scope. Full detail: SPEC.md, section 6.

## 5. Routines

Hipocampo assumes periodic rituals conducted by an AI agent under your supervision — not unsupervised automation. Two central rituals, both already covered by the Hipocampo skill (`skill/SKILL.md`, once personalized):

- **Staleness** — periodic check of expired `ttl`, different behavior per `temporality` (SPEC.md, section 5).
- **Consolidation** (inbox → knowledge) — loose capture becomes a document with complete frontmatter, always reviewed by you before final write (invariant 5 of SPEC.md — the agent never writes without an explicit request).

The skill also checks, at the start of a session, whether a new version of the methodology has been published in `hipocampo` and notifies you — it never applies the update on its own.

## 6. Before activating

Read the entire `DISCLAIMER.md` before treating any Hipocampo instance as the single source of truth for something that matters (compliance, financial decision, evaluation of a person). The methodology is a knowledge management system built on git + markdown + probabilistic AI — not a transactional database nor a technical access enforcement system beyond what GitHub itself guarantees.

## 7. Typical use cases

Three short, narrative walk-throughs of the methodology working as intended, once the mechanics above already make sense. For scenarios that specifically probe judgment under difficulty — including a real documented failure — see `docs/evaluation-scenarios.md` instead; these three are the ordinary path, not the edge cases.

**A typical week.** The frontmatter audit (SPEC.md section 5-B) runs first, most days — a deterministic scan that lists expired `ttl`s, missing fields, and deprecated vocabulary values in `meta/fila-de-manutencao.md`, deciding nothing on its own. The REM ritual (section 5-A) runs right after, in the same cycle: it consolidates whatever landed in `inbox/` into real documents, and works through the queue the audit just produced, one item at a time, always presenting the plan before writing anything (invariant 5). Once a week, the structural audit (section 5-C) looks at the repository as a whole — atomicity, positioning, and sensitive-data compliance — catching what the daily rituals aren't scoped to see because they operate document by document, not across the repository.

**Bringing outside knowledge in.** A user has notes from before they adopted Hipocampo — a folder of Google Docs, an old wiki export, a legacy tool's dump. None of it gets copied in directly, even if the content is already fine. Section 10 requires a fresh frontmatter, built for the current schema, and a body adjusted to the current atomicity and privacy rules — `revision_note` records what was preserved verbatim and what changed, and why (`decisions/0011`). The same discipline is reused, not reinvented, by Promote's elegant path (section 13) — migrating from outside the methodology and migrating between two of its own repositories are the same underlying operation.

**When two repositories need to talk.** A user with more than one instance (say, a personal one and a work one) writes a document in one that's genuinely relevant to the other. Rather than duplicating the content, the document gains a `related: ["$alias:path.md"]` entry (SPEC.md section 6) pointing across the boundary, and the target repository's `registry.md` — kept in whichever of the two repositories is the least restricted — records the alias so the reference actually resolves. The two documents stay independent from then on: updating one doesn't obligate updating the other, and neither copy is the "real" one at the other's expense.
